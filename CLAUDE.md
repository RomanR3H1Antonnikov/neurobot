# Промпт для Claude Code — AI-бот Артёма (генерация/редактирование медиа + чат + документы)

## Контекст проекта

Разрабатываем Telegram-бота для клиента Rehy Solutions. Бот — платный сервис для сторонних
пользователей: генерация и редактирование фото/видео/аудио через сторонние нейросети,
обычный чат-режим с ИИ, работа с документами, и система биллинга на кредитах.

Владелец бота (аккаунт в BotFather) — сам клиент. Bot token уже выдан и передан.
Разработку ведём мы, тестируем и правим совместно с клиентом на всех этапах.

Договор: 65 000 ₽ (60 000 ₽ при отзыве после запуска), срок 10 календарных дней,
три этапа. Полное ТЗ приложено ниже — следуй ему как основному источнику истины.
Всё, что не покрыто ТЗ, но обсуждалось с клиентом отдельно (см. раздел "Уточнения после ТЗ"),
имеет приоритет над письменным ТЗ, так как отражает более поздние договорённости.

## Технический стек

- Python 3.11+
- aiogram (Telegram Bot API)
- FastAPI (если понадобится веб-часть; на первом этапе не обязателен)
- SQLite (база данных — балансы, история операций, история диалогов чата)

- Реальный код передаётся клиенту целиком — пиши так, будто сдаём в чужие руки:
  чисто, с комментариями на ключевых местах, без хардкода токенов/ключей в коде
  (использовать .env)

## КРИТИЧЕСКИ ВАЖНО: архитектура подключения нейросетей — мультиагрегаторная

Изначально в ТЗ был зафиксирован единственный агрегатор gen-api.ru. После подписания
договора клиент попросил изменить архитектуру: **не завязываться на один агрегатор**, а
поддерживать несколько одновременно (aitunnel.ru, routerai.ru, KIE — на данный момент,
список может расшириться) и **выбирать самый дешёвый агрегатор для конкретной модели**
на момент запроса.

Требования к архитектуре:

1. **Слой абстракции над агрегаторами.** Создай единый внутренний интерфейс
   (например, `MediaProvider` / `AggregatorClient`), через который бот обращается
   к любой генерации, не зная деталей конкретного агрегатора. Каждый агрегатор —
   отдельная реализация этого интерфейса (адаптер), со своим форматом запроса/ответа,
   аутентификацией и обработкой ошибок.

2. **Таблица маршрутизации моделей.** Нужна конфигурация (в коде или в БД — на твоё
   усмотрение, но с возможностью клиента редактировать без глубокого погружения в код),
   которая сопоставляет: тип задачи (фото-генерация, видео-генерация, аудио,
   редактирование) → конкретная модель → через какой агрегатор её вызывать → стоимость
   у этого агрегатора. Бот выбирает самый дешёвый вариант для нужной задачи автоматически.

3. **Пользователь не выбирает модель вручную.** Он описывает задачу текстом (и опционально
   прикрепляет референсные фото/кадры — см. UX-референс ниже), бот сам определяет тип
   задачи и подбирающую модель/агрегатор.

4. **Смена или добавление агрегатора/модели — программная операция**, не через
   отдельную админ-панель (админ-панель в стоимость этого этапа не входит — см. договор).
   Но код должен быть организован так, чтобы добавление нового адаптера агрегатора было
   быстрой, локальной правкой (не рефакторингом всей системы).

5. Клиент должен будет **держать положительный баланс на каждом подключённом агрегаторе**
   отдельно — это его эксплуатационная зона ответственности, не наша. Бот не должен
   валиться при недостатке средств на стороне агрегатора — должен ловить ошибку и
   сообщать пользователю нейтральным текстом ("сервис временно недоступен, попробуйте
   позже"), без утечки технических деталей.

## Функционал (по ТЗ, актуализированный)

### 1. Генерация и редактирование медиа
- Генерация фото, видео, аудио с нуля по текстовому промпту
- Редактирование существующих медиа (замена фона, апскейл, озвучка — набор уточняется
  по факту выбранных моделей)
- Базовый набор — одна-две модели на тип контента в первой версии

### 2. Чат-режим
- Обычный диалог с ИИ, без персонажей и без долгой памяти между сессиями в базовой версии

### 3. Работа с документами
- Пользователь присылает файл (PDF, Word, таблицу) + текстовое задание
- Бот читает содержимое и выполняет задачу (резюме, перевод, поиск, редактура и т.д.)
- Подход общий для всех типов файлов, без узкой заточки под сценарии

### 4. Биллинг и баланс
- Индивидуальный счёт в кредитах на пользователя
- Списание за генерацию — фиксированная сумма по типу контента
- Пополнение — через встроенный в Telegram платёжный провайдер (клиент подключит
  на финальном этапе, см. "Порядок реализации" ниже)
- Лимиты на пользователя — защита от резкого перерасхода бюджета за короткое время
- При нехватке средств — понятное сообщение, генерация не запускается

## UX-референс (важно для восприятия ботом пользователя)

Клиент прислал референс — бот @GPT4Telegrambot. Взять оттуда **модель ответа и
взаимодействия**, не точные тексты:

- Перед генерацией показывается карточка с текущими настройками (промпт задан/не задан,
  выбранные параметры) и рядом — инлайн-кнопки для их изменения (формат, качество,
  длительность, наличие звука и т.п., в зависимости от типа медиа)
- Явная кнопка "Начать генерацию" — генерация не запускается автоматически по вводу текста,
  пользователь должен подтвердить
- Кнопка "Назад" для возврата к предыдущему шагу настройки
- Клиент просил **немного упростить восприятие** относительно референса — сделать
  интерфейс менее перегруженным кнопками, чем в примере. Не копируй один в один
  количество опций — уменьши там, где это не критично для UX.

## Этапы реализации (согласно договору, суммарно 10 дней)

1. **Этап 1 (~4 дня):** биллинг, интеграция с агрегаторами (мультиагрегаторная
   архитектура, см. выше), чат-режим
2. **Этап 2 (~3 дня):** работа с документами
3. **Этап 3 (~3 дня):** тестирование полного цикла (пополнение → генерация → списание),
   запуск

## Порядок реализации — важные детали по срокам

- **Начинай с базовой архитектуры бота и слоя абстракции над агрегаторами** — это
  сегодняшняя задача.
- **Оплата (платёжный провайдер, например Tribute) подключается в последнюю очередь**,
  по явной договорённости с клиентом — чтобы не тратить бюджет на тестовые платежи
  раньше времени. До этого момента баланс/кредиты можно тестировать через ручное
  начисление в БД (тестовый режим).
- Данные от gen-api.ru / выбранных агрегаторов ожидаются от клиента в течение
  ближайшего дня-двух после начала работ — закладывай архитектуру так, чтобы
  подключение реальных ключей агрегаторов было последним шагом, не блокирующим
  разработку остальной части.

## Критерии приёмки (из ТЗ)

- Пополнение баланса и списание кредитов работают корректно по каждому типу генерации
- Чат-режим отвечает в режиме диалога
- Бот принимает документ и выполняет текстовое задание по его содержимому
- Полный цикл "пополнение → генерация → списание" работает без ошибок
- При нехватке средств или превышении лимита — генерация не запускается, пользователь
  видит понятное объяснение
